# Native DFlash2 on two V100 cards: IQ3_S, 2026-10-20

## Result

Native DFlash2 works with the regular Qwen3.8-Flash-Next-GSQ-RCO IQ3_S target.
It does not give a general speed increase on this system.
It increases mean acceptance by 2.95–6.15% in the three complete matched datasets.
Its request throughput is 1.45–6.92% lower than coupled MTP in those datasets.
Do not treat the model card's 6–17% acceptance gains as a local speed guarantee.
Keep the approved MTP configuration for daily use.

The user stopped the large acceptance sweep.
No further acceptance-sweep requests ran after the stop instruction.
DFlash2 completed five datasets with 128 requests each.
Coupled MTP completed three datasets with 128 requests each.
MTP also completed 30 MBPP requests before cancellation.
Those 30 requests are not used in the tables below.
The interrupted request is not counted.
The MT-Bench MTP arm and the point-mass acceptance arm did not run.
This report is not a complete five-dataset matched comparison.

## System and source

- GPUs: two Tesla V100-PCIE-16GB cards, 16,384 MiB each.
- Power limit: 175 W on each card. Clocks were not locked or logged continuously.
- GPU order: `[0, 1]`. GPU 0 uses PCIe Gen3 x4 and layers 0–15.
  GPU 1 uses PCIe Gen3 x16 and layers 16–47.
- CPU: Ryzen 5 3600, six cores and 12 logical CPUs.
- RAM: 98,798,956 KiB, about 94.2 GiB.
- Model storage: Kingston OM8PDP3256B-AI1 NVMe, ext4.
  The checkout uses a Samsung PSSD T7 with ext4.
- OS: Linux 7.0.0-38-generic. GCC: 13.3.0.
- Driver: 580.178.04. CUDA toolkit: 12.8.93.
  The driver's reported maximum CUDA version is 13.0, not the build toolkit.
- Implementation: `9de841284d9ae487bc5bd965427453cab1bb057e`.
- Measured executable MD5: `30f022f52072b737e73a11aea64f4672`.
- Build: Release, CUDA architecture 70, native experts enabled.
- Target: regular, non-abliterated Qwen3.8-Flash-Next-GSQ-RCO, IQ3_S.
- Draft: `incoai/Qwen3.8-Flash-Next-DFlash2`, revision
  `a22a1744e85c17364dcc54a6a420af7135d4c7f6`.
  Its source weights are BF16. The native path rounds weights and matrix inputs
  to FP16. It keeps accumulators, outputs, other activations, residuals, and
  draft K/V in FP32. This is not bitwise BF16 execution.

## Controls

All local arms use the same target assets and tokenizer.
They use INT8 target K/V, a 524,288-token context limit, and YaRN factor 2.
They use the measured layer split of 16.
Expert-cache and prefill selection are automatic.
The VRAM reserve is 1,024 MiB. Elastic VRAM growth is off.
Vision is enabled, but the requests contain no images.

`STRATA_ROUTE_RESIDENT=0` and `STRATA_ROUTE_TAIL_SKIP=0` disable approximate routing.
Prompt, RAM conversation, and disk conversation caches are off.
Each request reads its whole prompt.
Suffix drafting and lookup chains are off.
Server recovery rules are off. The repeat-stop token limit is zero.
No other client, compiler, or GPU workload runs during a measured arm.
The server restarts between arms. Loading and readiness are outside the measurements.

DFlash2 block 4 and MTP use a maximum verify window of four tokens.
They use pipeline 1 unless the short-suite label says pipeline 2.
DFlash2 block 8 uses a maximum verify window of eight tokens.
AR has no drafter and emits one token per decode step.
Its native-pack command still requests `--spec 4`; that does not enable drafts.

## Matched acceptance

The primary MTP baseline uses `STRATA_SPEC_COUPLED=1` and `STRATA_SPEC_PROB=1`.
Its sampled draft distribution and exact rejection sampling are active.
The startup check found no fallback to argmax drafting.
The model card does not give its MTP launch command.
The pinned SGLang default uses a different, point-mass draft rule.
Do not call the local coupled baseline an exact reproduction of that command.

Each dataset uses the reference prompt format and a full-corpus shuffle with seed 42.
Each completed cohort has 128 first-turn requests.
MT-Bench repeats its shuffled 80-row corpus and uses only the first turn.
Each dataset has a separate 64-token warmup, which is not measured.
Sampling uses temperature 1.0, top-p 0.95, top-k 20, and `xhigh` reasoning.
The output limit is 4,096 tokens. The local seed is 4200 plus the selection ordinal.
The published reference does not specify those local seeds.

Acceptance is `engine_generated / verification_steps` for each request.
The table gives the mean of those request values, not a pooled token/window ratio.
The runner requires exactly one engine generation per request.
It reads the exact step count from that request's decode log span.

## Implementation checks

Eight focused tests passed: DFlash2 overflow, DFlash2 attention, verify parity,
sampler parity, speculative verify parity, two other sampler variants, and
probability verification.
The attention test covers ring wrap, grouped-query heads, empty context,
full context, strict mask boundaries, and guarded output buffers.

A separate numerical smoke run loaded the real five-layer draft weights.
It used three synthetic context rows and an independent NumPy implementation.
The maximum absolute hidden-state difference was 0.026630.
The relative L2 difference was 0.0013545.
The realized-predecessor conditional probabilities and sampled path matched.
This is a numerical check, not a claim of bitwise reference parity.
A separate live integration check exercised a 22,032-token prompt and a cached follow-up.
That cache-on check is not part of the cache-off performance tables.

The native draft performs one parallel five-layer block pass.
It does not run an MTP-like sequential draft chain.
It uses sharded top-k selection, a device-side conditional selector, and FP32 attention.
The approved daily executable was not replaced with the unmerged implementation.
The daily abliterated model and its matching pack and tokenizer were restored.
The service reported a loaded model and answered an authenticated inference request.

## Reproduction and limits

Use [the operation guide](../docs/DFLASH2.md) and
[the runner](../bench/run_dflash2_bench.py).
Use a separate private test configuration. Do not copy credentials into results.
A full 128-request cohort across five datasets is 640 measured requests per arm,
plus warmups. Do not use that sweep for a routine implementation check.
Use a one-record custom smoke workload for that purpose.

The published model-card comparison uses an FP8 target on GB300.
This report uses IQ3_S on two V100 cards with the controls above.
The observed local acceptance gains do not establish the full published 6–17% range.
They do not establish a throughput improvement.
Only the three complete matched datasets support the local relative-change tables.
